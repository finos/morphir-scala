# Layered Decorations

**Not present in the v4 spec draft.** Decorations attach metadata to IR nodes without modifying the IR, stored in a
layered, composable system alongside it. This is v3's decoration mechanism reworked — see the `morphir-elm` bundle's
decorations concept for what it replaces.

## Design principles

- **Separation of concerns** — the core IR stays clean; decorations are additive.
- **Layered** — multiple sources with defined precedence.
- **Flattened** — FQName keys for direct lookup, not a mirrored directory structure.
- **Type-safe** — values are validated against Morphir-defined schemas.
- **Deep merge** — the same node and decoration type from several layers are deep-merged.

"Flattened" is a deliberate reversal of the rest of the VFS design: the IR mirrors its namespace onto directories,
while decorations do the opposite and key one file per decoration type by full FQName. Decorations are looked up by
node, not walked by namespace.

## Layout

```
.morphir-dist/deco/
├── format.json             # Schema registry, layer list, layer priorities
├── schemas/                # Local schema cache
│   ├── documentation.ir.json
│   ├── deprecated.ir.json
│   └── tags.ir.json
└── layers/
    ├── core/               # From compilation — doc comments, source annotations
    │   ├── manifest.json
    │   ├── documentation.json
    │   └── deprecated.json
    ├── tooling/            # Generated by linters, analyzers, inference
    └── user/               # Hand-authored
```

## Layers and precedence

| Layer | Priority | Source |
| ----- | -------- | ------ |
| `core` | 0 | Compilation — extracted from source |
| `tooling` | 50 | Analysis tools |
| `user` | 100 | Manual authoring |

The gaps in the numbering are intentional: projects may define custom layers between them, for example
`team-standards` at 25 and `overrides` at 200.

## Merge semantics

Values for the same node and decoration type are deep-merged, higher priority winning.

| Value type | Behavior |
| ---------- | -------- |
| Primitive | Higher priority wins |
| Object | Deep merge recursively |
| Array | Concatenate, higher priority first; dedupe optionally |
| Null | Higher priority wins — so a higher layer can **unset** a lower one |

The merge is per-field, not per-node. A `core` layer contributing `details` and a `user` layer contributing
`examples` and a better `summary` produce a record with all three, the user's `summary` winning.

## Schemas

A decoration type is defined by a **Morphir type**, not a JSON Schema. `deco/format.json` holds a registry mapping
each decoration type to a `displayName`, a `localPath` into `schemas/`, an optional `remoteRef` into a registry
(`morphir://registry/decorations/documentation@1.0.0`), and an `entryPoint` FQName naming the type that defines the
shape.

Schemas are cached locally for offline access, with CLI support to `sync`, `update`, and `verify` them against the
registry.

## Targets

```
TypeTarget(fqname)      // my-org/project:domain#user
ValueTarget(fqname)     // my-org/project:domain#create-user
ModuleTarget(package, module)
PackageTarget(package)
```

Module and package targets are how the design compensates for `ModuleDefinition` having no `doc` field — see
[Module and Package Decisions](/design/module-and-package-decisions.md).

## Standard decoration types

| Type | Shape |
| ---- | ----- |
| `documentation` | `summary`, `details`, `examples`, `params`, `returns`, `throws`, `see`, `since` |
| `deprecated` | `since`, `replacement` (FQName), `reason`, `removalVersion`, `migrationGuide` |
| `tags` | `List String` |
| `alias` | `name` plus optional `target` platform, for code generation |
| `nativeHint` | `platform`, `implementation`, optional `importPath` |

## Protocol

The daemon exposes decorations over JSON-RPC: `deco/read` (merged values for a node, with a `sources` map naming
which layers contributed), `deco/write` (to a named layer), `deco/list`, and `deco/layers`.

`deco/read` returning provenance alongside values is the payoff of the layer model — a UI can show that a summary
came from `user` while its details came from `core`.

## Validation

Validation checks that a value conforms to its schema, that the target FQName exists in the IR, that no decorations
are orphaned by a deleted target, and that schema versions are compatible.

## Migration

The v3 format stored all decorations in one file keyed by a `My.Package:Foo:bar` string. A migration command moves
such a file into `deco/layers/{layer}/{type}.json`.
