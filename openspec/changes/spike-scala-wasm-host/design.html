spike-scala-wasm-host

2026-11-10 | Experiments in progress | First six-configuration checkpoint retained after 45 minutes

Compare Endive's interpreter, GraalWasm and an Extism C API backend through JDK FFM. Check kyo-ffi first for the native binding and prove that path early, before implementing a complete Extism adapter over either JVM engine. The first rejection gate for every candidate is a native executable loading a guest it was not built with. A successful run supports a bounded Scala-host experiment; replacing the Morphir CLI needs a separate decision.

Context

See proposal.md for motivation and scope and the qualification specification for observable requirements. The existing MEP module is an Elm extension provider. It is not a host, and Native Image support for that provider proves no Wasm embedding compatibility.

The local build pins Scala 3.9.0 and Kyo 1.0.0-RC7. KB and squire already use KyoCommand and kyo-case-app. The machine reports Darwin arm64, Oracle GraalVM 25.0.1 and Native Image 25.0.1. These are inspected prerequisites, not execution results.

Extism exposes its native runtime through a C ABI; the inspected Java SDK uses JNA. The Scala-owned FFM experiment reuses libextism 1.41.0. Direct downcalls and retained upcalls pass on JVM and Native Image 25.0.1, with shared-arena flags, explicit foreign descriptors and matching C layout assertions. The RC7 Kyo FFI generator rejects the callback's typed pointer argument; its failure receipt justifies the direct fallback.

The mirrored upstream IR sources are pinned to 4d5e5c06a7cf269c5f86b050a16a6f82bb5c29bc and do not contain the current worker contracts. Current upstream evidence is therefore pinned separately below. Historical WIT extension designs and older Rust runtime budgets must not silently become this spike's acceptance contract.

Goals and non-goals

The first checkpoint's raw samples and elapsed-time receipt are retained under .dev/.sdlc/scala-wasm-host/out/. All six basic core-Wasm probes pass. Real SDK and Python legacy MEP flows pass on Endive and direct FFM on both targets. GraalWasm refuses their absent memory maxima. The FFM growth test fails the absolute ceiling requirement because libextism's allowance resets per call. The pinned MoonBit source build is blocked by the installed compiler/core combination. These findings do not substitute for the remaining experiments or qualify a CLI replacement.

The completed footprint collection retains 144 runs, with 120 successes and 24 GraalWasm real-workload admission failures. It includes five fresh-process trials, separate no-RSS-sampler timing trials, 20-cycle parent retention and two-worker observations for each configuration and workload. Endive and FFM also pass eight SDK/Python MCK guest runs with independent report validation. The generated offline report at .dev/.sdlc/scala-wasm-host/out/report/index.html binds charts to raw samples and distribution hashes. Native installed sizes are 28.52 MiB Endive, 71.73 MiB GraalWasm and 51.25 MiB FFM including its library. The leading bounded-host candidate is Endive; FFM's memory-ceiling failure remains disqualifying for that requirement.

Fresh-process measurements do not flush OS or runtime caches. Runtime.totalMemory is recorded under the historical raw field heapCommittedBytes; it is runtime-reported heap capacity, not measured OS commit or RSS. Native Image's large reported capacity must not be presented as resident usage. Fully instrumentation-free timings and exact native allocation attribution are unavailable; separate no-RSS-sampler runs still emit phase/heap/GC events.

The design asks whether each runtime can execute real Morphir guests after Native Image compilation, whether Kyo can own the lifecycle, and what the delivered host costs in executable/package bytes and memory over time. Each answer needs its own evidence. Functional success alone does not settle whether the footprint suits a CLI.

The spike does not compile Scala to Wasm, use Scala Native, recreate the retired Scala CLI, implement registry acquisition, or design a new extension protocol. Component Model hosting is reported separately. Full rich Ion model preservation, lossless conversion, workspace services and installation policy remain outside a minimal host result.

Decisions

ABI-1. Test today's guest ABIs before Component Model work

The selected compatibility baseline is the current MoonBit host worker specification at 661e770e7af0d40b0f7cb44909e3d18e6c11b7cf, together with root MEP contracts at 9690dfc3761e1cbe1cd3d6fa327a5e082b9892ac. Both profiles are core Wasm and export handle: () -> i32. Neither requires Component Model support.

A small fixture is still useful for import signatures, memory and cancellation failures.

MEP legacy 0.1 and 0.2.0-draft.1 are separate qualification tiers. The latter requires bilateral model transport admission. Start with legacy lifecycle and JSON operations; attempt the JSON model tier on the same guests after that passes. A legacy pass alone earns only a legacy-scoped result. Preserve numeric request IDs without narrowing unsigned 64-bit values to a signed Long, and test Unicode and empty string IDs.

RUN-1. Use a minimal adapter per runtime and preserve dependency isolation

Put unpublished JVM-only code under spikes/wasm-host/, with separate Endive, Graal and Extism-FFM configurations. The common contract loads verified bytes, inspects imports/exports, opens a private session, sends bytes and closes the session. Runtime-specific types stay in restricted internal packages. Return Kyo Result and Maybe at any reusable boundary. Do not make a published plugin API during a spike.

Endive 1.2.0's interpreter is the default first experiment because it can load Wasm without generating Java classes. Its JVM runtime compiler generates bytecode dynamically; that is not the default Native Image path. Build-time compilation is a useful secondary experiment for bundled extensions, but cannot satisfy loading an unknown extension after host compilation. Redline adds experimental native-code and FFI concerns and is deferred.

GraalWasm uses the Polyglot API. Pin Polyglot and language dependencies to 25.0.1 for the installed JDK, verify resolution, and use the documented module-object instantiation API for that release. Later online documentation is discovery evidence only. Test host callbacks with explicit proxies/import objects before trying an Extism adapter. Prefer community artifacts where compatible and record licenses and runtime mode.

The existing MorphirNativeImage overrides nativeImageClasspath to use an assembly. Oracle's embedding guidance excludes uber JARs from Native Image polyglot builds. Override the classpath in the spike's Graal-specific trait to retain individual dependency JARs, service registrations and resources. Do not change the existing Elm packaging helper or force Graal onto the Endive classpath.

FFI-1. Check kyo-ffi before writing direct FFM bindings

First resolve kyo-ffi and kyo-ffi-codegen at a version compatible with the repository's Kyo pin. Upstream documents a plain Scala FfiGenerator.generate entrypoint usable from Mill, so using this layer does not require introducing sbt. Separate compilation of binding declarations from generated implementations to avoid a TASTy generation/compile cycle. Generated sources and native resources are Mill task outputs.

Check whether that pinned generator can express Extism's opaque handles, pointers, fixed-width uint64 sizes, callback signature, retained user data, destructor callback, and tagged struct/union ExtismVal. Obtain layouts from the matching C header and target ABI, including padding; never assume Windows C long is the same as uint64_t. If generation, retained-callback support or Native Image metadata cannot pass within the timebox, record the mismatch and use a minimal direct java.lang.foreign binding. Both are implementations of the same FFM candidate, not additional runtime candidates.

Bind only the required API first: plugin create/call/free, output length/data, errors and the matching creation-error free, function registration/namespace/free, current-plugin memory access and cancel-handle/cancel. Pin a released libextism binary and its matching header; the inspected header source at 051b765bb6abe4fe95d5e4f489f03ad7b137edbc is discovery evidence, not an assumed binary ABI. Check the release's fuel-limit API, per-call reset semantics, timeout and memory options rather than infer them from function names.

Model guest calls as blocking, callback-capable downcalls. Do not use critical/no-callback shortcuts for handle. Retained upcall stubs, user data and callback arenas belong to the session and remain live after registration returns. Borrowed native output and error pointers do not escape: check unsigned lengths and bounds before conversion/copy, and copy accepted responses before a later call, reset or teardown can invalidate them. Do not free a borrowed plugin error as though it were a creation error.

Use small synchronous callbacks over private session state; do not suspend a Kyo effect across an arbitrary C callback frame. Validate guest offsets and lengths, capture callback failures inside the upcall, and report them through a bounded host/session error path. No Scala exception crosses the C boundary. Verify callbacks after GC pressure, repeated calls and multiple sessions.

Cancellation runs through Extism's cancel handle from another thread and must be observed to stop the call. A Kyo interrupt or a successful cancel return is not sufficient evidence. Stop admitting calls, request cancellation, wait for in-flight calls and callbacks, then release plugin/function resources according to the pinned API's ownership rules, followed by callback arenas and the library. Keep the parent-controlled worker termination fallback. Never free a plugin while its native call is running.

FFI-2. Qualify Native Image and the delivered native runtime together

Enable native access for the binding's module, or ALL-UNNAMED when the spike uses the classpath. Register each downcall/upcall descriptor or supported static upcall target at Native Image build time using the pinned release's metadata/Feature API. Load libraries and create live pointers/arenas at runtime rather than preserve build-machine addresses in the image heap. Preserve generated metadata resources when packaging.

The inspected kyo-ffi native-image.properties includes shared-arena and native-access flags. Verify what the resolved version actually ships and what GraalVM 25.0.1 requires; a successful help command is not evidence of shared-arena close, retained upcalls or cancellation. Repeat the complete create/callback/call/cancel/free proof in the native binary, then load a second unbundled guest without rebuilding.

Mill acquires verified libextism artifacts for the selected OS/architecture and records dependent libraries, licenses and digests. Use an explicit verified path or controlled bundled-library extraction, not an ambient loader search path or a guest-controlled override. Test the deliverable from a clean location with deliberately mismatched/missing library cases. A native executable plus a .dylib/.so/.dll is a valid measured distribution, but is not a single-file executable. Extism's engine may compile guests at runtime independently of the Native Image host; record its mode and executable-memory requirements.

Qualify extism-kernel-v1 first on this candidate. Its C plugin-call return/error convention is not automatically the byte profile's positive-length and negative-sentinel contract. Probe that profile independently and record unsupported behavior explicitly rather than claim that the C API covers every exported core-Wasm function. Compare all three candidates on identical Extism guest bytes; compare byte-profile results only where the adapter actually supports them.

KYO-1. Own sessions and workers through Kyo scopes

Use KyoCommand plus CommandsEntryPoint, following the KB and squire examples. Keep synchronous guest invocation on a dedicated carrier thread inside the worker. Runtime instances and their state must never migrate between concurrent calls. A session processes requests serially; parallel sessions get independent runtime instances and callback stores. Share parsed code only where the pinned runtime permits it.

Use Kyo scoped finalizers for contexts, native handles/arenas, streams, executors and worker processes. Measure cancellation propagation into the running guest: Kyo fiber interruption alone does not establish carrier-thread interruption or engine termination. The parent enforces a hard worker deadline, requests interruption/engine cancellation, escalates to termination within a fixed grace period, and waits for process exit. The JVM launch uses the pinned Java plus classpath; the native launch uses its own executable and verified runtime libraries where required.

Proposed spike commands are probe, qualify and worker. Require explicit runtime, guest path, report path and relevant limits. They are names for an experimental executable, not additions to the installed morphir command. Ordinary output can be JSON receipts; worker stdout is exclusively framed MEP. Usage, guest failure, deadline and user cancellation have distinct statuses.

LIM-1. Match the selected host's authority and report exact limits

Use a 256 MiB linear-memory ceiling, including modules without a maximum. Bound MEP payloads at 64 MiB before host copies and accumulate bounded diagnostic tails. The selected worker baseline has 30-second Extism and 10-second byte-profile call deadlines. Use shorter deadlines in synthetic runaway tests, recording the configured values. Include parsing, validation and start-function execution within the parent worker lifetime budget.

The current worker baseline uses per-call instruction budgets of 5,000,000,000 for the model line and 1,000,000,000 for legacy/probes when the engine meters. It explicitly permits a receipt to say metering is unavailable. Preserve the supported range through 2^53 - 1 and never silently narrow budgets to Int. Endive exposes an unsafe per-instruction interpreter listener; assess its correctness and overhead before calling it fuel. Graal statement limits must not be represented as equivalent Wasm instruction counts without proof.

Reject unknown imports and wrong signatures before instantiation. WASI gets no directories, empty arguments/environment/stdin, bounded diagnostic writes, clocks and random bytes. Other operations fail without reaching the host. Extism HTTP access fails, config lookup is empty, and variables/cache are session-private. Use an explicit allowlist and virtual/denying filesystem rather than assume a general WASI library's defaults meet these rules.

EVI-1. Record evidence before choosing the runtime

Keep receipts in .dev/.sdlc/scala-wasm-host/out/. Mill owns acquisition, fixture compilation, invocation and report generation. Vendor original small WAT fixtures with source/provenance; generate their binaries as task outputs using pinned tools. Do not add Python, Node, Ruby or shell logic for qualification.

Each receipt records repository revision and dirty state, OS/architecture, JDK and native-image versions, Mill/Scala/Kyo/runtime coordinates, dependency hashes, executable and guest digests, runtime/compiler mode, commands, input corpus digest, requests/responses or their bounded retained files, enforced limits, phase timings and errors. The FFM receipts also identify the binding/codegen version or direct-FFM fallback, C header and native-library digests, loader policy, dependent libraries and native-call registrations. The matrix has six runtime/target cells, each subdivided by tested ABI, and every observation begins as not-run. Missing acquisition, compiler or callback support is blocked or failed evidence, never a pass.

Capture initial executable bytes and probe memory as soon as an artifact runs, with its limited probe scope attached. After correctness passes, collect the complete footprint and timing protocol below. Record Native Image build wall time and build-process peak RSS separately from execution. No size, memory or performance threshold is invented for this spike.

Use the pinned upstream MCK generic or language-specific guest kit when the selected guest supports it, and retain both executable-run and independent report-check output. Those kits qualify bounded guest behavior through a host; they explicitly do not establish full independent-host admission conformance. Add the worker-specific rejection/cleanup observations above to cover the missing questions.

MEM-1. Measure the executable and the whole delivery

For every produced configuration, retain a file inventory with digests and logical byte sizes. Report executable-only size for native hosts, launcher/application-JAR bytes for JVM hosts, full installed application distribution bytes and compressed package bytes using the same archive format and compression settings. Include native libraries, required runtime resources and bundled guests in the applicable totals. Record debug symbols separately and state whether they are shipped; record stripping, optimization, CPU target, GC and monitoring options. Compare comparable delivery builds, preserving the existing compatibility CPU target.

For a JVM distribution, state whether Java is bundled. If provisioned externally, report that runtime's identity and installed size separately rather than equate a small JAR with the whole deployment. Identify system-provided libraries as external requirements. A failed native build has no executable-size result; never plot it as zero bytes. Snapshot the artifact identity before profiling so measurements and file inventory describe the same build.

MEM-2. Profile the parent and workers through the lifecycle

Use OS process-memory observations for the delivered configuration as the common baseline. Reuse appropriate process discovery, PID deduplication and aggregate-RSS logic from mill-build/src/millbuild/LinkerBenchmarkProcess.scala after checking its sampling behavior. Its build-oriented inclusion of the orchestrator must not pull Mill, the compiler or the sampling tool into runtime totals. Existing LinkerBenchmark heap/GC observations are a possible supplementary source, not a complete process-memory measurement.

MEM-3. Keep accounting and instrumentation limits visible

Record JVM/native heap limits, GC policy, runtime cache settings and guest ceilings. Capture heap used/committed/max, GC observations and engine/guest memory counters where the pinned implementation exposes them. Separate virtual reservation and off-heap categories rather than force them into a fabricated exact total. OS RSS/footprint remains required for Extism: runtime Native Memory Tracking does not cover arbitrary third-party native allocations.

Start with delivery-build OS measurements. If heap/JFR/NMT or allocation diagnostics require extra build flags or runtime instrumentation, run a separately identified diagnostic configuration and record its binary bytes and observed overhead. In particular, enabling Native Image NMT changes the build; verify exact 25.0.1 support before using it. Diagnostics must not write into a worker's MEP stdout. Missing category support is an explicit gap, not zero allocation.

Observe normal cleanup without forcing GC or flushing caches. Optional forced-GC/cache-reset experiments must be separately labeled. Retained RSS may reflect caches, allocator retention or shared mappings and is not sufficient to prove a leak. Treat sustained growth across cycles as evidence for a bounded follow-up investigation and correlate with available allocation/heap observations. Build-time memory, guest linear-memory ceilings and total runtime process memory remain distinct figures.

MEM-4. Deliver charts with their raw evidence

Generate a standalone offline HTML footprint report alongside JSON/CSV samples under .dev/.sdlc/scala-wasm-host/out/, using Scala/Mill. Include grouped size bars for executable/application, installed application and compressed package sizes; show bundled or externally provisioned runtime bytes separately. Include aligned memory timelines with startup/load/call/cleanup markers, per-process and aggregate series, phase peak/idle comparisons, and a retained-memory-by-session-cycle chart.

Cover all six candidate/target configurations in the report, grouping comparisons by matching ABI/workload and target OS/architecture. Mark blocked, failed-before-measurement and not-run observations as unavailable with their reasons; omit numerical bars/lines for those cells. Every chart identifies units, artifact/corpus digests, build/runtime settings, repetition counts and measurement method and links its raw observations. Present size, memory, latency and functional coverage together so a smaller binary cannot conceal extra native-library bytes or much higher worker memory.

Experiment order

COMPILER-1. Host the MoonBit compiler itself

The isolated polyglot follow-up uses aligned GraalJS/GraalWasm/Polyglot 25.5.5.0.3 and digest-verified GraalVM Community JDK 25.0.5.0.3. Both JVM and Native Image compile a tiny MoonBit function through the upstream Wasm compiler and execute its emitted 173-byte Wasm with result 42. A JavaScript compatibility runtime supplies bounded file access without Node or native moonc. The measured native build produced a 129.59 MiB executable in about one minute with 6.26 GiB build peak RSS. Runtime sampling and no-sampler timing remain separate from build measurements and from the original six-host matrix.

The separate compiler report retains twelve positive/negative checks and twenty fresh-process trials. JVM/native installed host sizes are 92.09/129.59 MiB; compressed host packages are 49.20/57.36 MiB. Shared compiler/core/licenses add 15.78 MiB installed and 3.33 MiB compressed, and the JVM's external JDK is 633.62 MiB. Median process-to-verified-result latency is 1.902/0.637 seconds. Separate sampled trials observe median parent peak RSS of 973.23/316.14 MiB. The compiler has no workers, so parent and aggregate RSS coincide. Memory trials hold each phase for 200 ms; timing trials have no holds or RSS sampler. Warm compiler throughput, private/committed memory and 20-cycle compiler retention remain unavailable. The report is .dev/.sdlc/scala-wasm-host/out/report/polyglot-compiler/index.html.

The unmodified compiler fails inside GraalJS's Wasm callback wrapper. A minimal repeated-import regression reproduces this when arity decreases from three arguments to two; increasing arity succeeds. The optional adapter rewrites import names to unique aliases and forwards the same JavaScript callbacks. Receipts retain original/adapted SHA-256 hashes and verify every non-import section is byte-for-byte unchanged. This workaround is part of the tested compiler profile and is not a claim of unmodified upstream compatibility.

The released compiler bundle v0.10.19+97801ee1b is digest-verified. All six original Morphir adapters refuse its GC array types before engine execution. Independent inspection finds 73 compiler imports, comprising 72 functions and one exception tag, including 66 bindings entries. The release repository revision and compiler build suffix are separate identities; the core is content-pinned by archive digest. The tiny-source proof does not qualify all compiler string builtins, multi-file/core builds, cancellation or long-lived compiler sessions. Those checks remain in task 8.3.

This experiment is distinct from compiling a Morphir MoonBit guest with an installed native toolchain. Acquire the released MoonBit Wasm compiler bundle with its digest, source revision, core/moon revision markers, licenses, loader and companion modules. Inspect actual imports and required Wasm features before adding an adapter. The official toolchain uses wasm_of_ocaml and a JavaScript host interface; it must not be assumed to be a standalone WASI command or an Extism plugin.

Attempt loading the pinned compiler with every existing JVM/native host. Distinguish rejection by our Morphir adapter from evidence about the engine itself. Record missing GC/reference/exception/string features, module linking or JavaScript runtime imports by name. If a bounded compiler adapter is feasible, expose only a read-only toolchain/core and a temporary writable workspace, with bounded diagnostics and parent-controlled cancellation. Deny ambient filesystem, process spawning, environment and network access. Any required authority beyond that is a recorded blocker.

On a supporting configuration, compile a pinned source fixture, load its resulting core Wasm and verify its expected semantic result. Include invalid source, repeated compilation, independent workspaces, cleanup and unchanged native-host digest checks. A multi-file/core-library example follows the minimal function. Report compiler guest load/compile latency, package bytes including auxiliary modules/core, and parent/worker memory separately from Morphir guest profiles. A compiler hosted by Node or native moonc does not pass this experiment.

SPEED-1. Compare execution speed by workload

The verified matrix retains 120 runs, 110 successful runs and 11,000 measured calls. Only GraalWasm's ten real Python trials are refused. Median-of-trial-medians for native Python compile is 7.7092 ms Endive and 0.0598 ms FFM. GraalWasm leads the measured compute/memory kernels, while byte-callback overhead and real compilation produce different comparisons. Preserve these workload distinctions and existing qualification failures. The first interrupted matrix used insufficient memory headroom for Extism input allocation and is retained outside the verified result set.

Use identical Wasm bytes and inputs for callback-boundary, integer-compute and linear-memory-loop cases. Check deterministic results, consume computed checksums and retain declared work units so a dead computation cannot masquerade as execution speed. Include the same pinned Python legacy MEP compile workload and add MoonBit compiler work only where compiler hosting actually passes. These are measurements of the current host stacks, including their adapters and default safety mechanisms, rather than isolated engine instruction costs.

Use five fresh processes per configuration/workload, twenty recorded warm-up invocations and one hundred measured invocations per process. Rotate configuration order between trials, run measurements serially on the same hardware, and disable RSS sampling and artificial holds. Record the exact warm-up protocol without claiming JIT stabilization, along with heap/GC phase-event and clock instrumentation, compilation-cache policy and FFM fuel. Preserve the earlier ten-warm-up footprint timings separately. Report startup-to-first-result, trial medians/ranges, pooled p50/p95/p99 latency and sequential invocation throughput with clear denominators. Show early/late batch timing trends rather than conceal tiering or drift. Do not pool different workloads into a universal speed score or drop failed cells.

Migration plan

There is no user migration or deployment. The spike stays unpublished and opt-in. If rejected, remove the module and its build wiring while retaining the archived experiment record. If successful, propose a separate production host change with the chosen runtime and supported contracts. Promote durable conclusions into the KB only after evidence exists.

Open questions

After the minimum qualification, determine acceptable startup/RSS/distribution size for a CLI, which additional platforms deserve native packaging, and whether future WIT/component hosting warrants a separate experiment. None is required to test the selected current guest ABIs on this machine. Runtime feasibility questions themselves are the experiments above, not unresolved implementation choices.
