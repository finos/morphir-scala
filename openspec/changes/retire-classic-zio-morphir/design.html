Context

See proposal.md for why. Requirements are in ir-v3-ingestion and published-library-families.

What the code shows today:

  • The classic family is the root morphir module (238 source files) plus interop.zio.json, interop.borer, model.lowering, runtime.classic, tools, tests, testing.zio and testing.generators. Seven of them publish for the JVM and Scala.js: 14 artifacts.
  • Outside the family, only knowledge.logic depends on it, and only nominally: it compiles and tests without the root module.
  • v3 morphir-ir.json reaches the Kyo code model in two steps: the classic ZIO JSON decoders build classic IR objects (format versions 1, 2 and 3), then V3Lowering converts those to the code model. Nothing else calls V3Lowering.
  • The Kyo side already writes v3 (model.compat.v3, V3WireProjection, JVM only) and reads and writes v4 (CodeModelCodecs, a derived layout). It has no v3 reader and no evaluator.
  • examples/morphir-elm-projects builds real morphir-elm IR through the Mill Elm plugin. Only the classic runtime fixtures (ClassicRuntimeTestFixtures) consume it.
  • finos/morphir ships the Morphir Compatibility Kit (MCK). morphir mck run --suite ir --adapter <exe> drives an implementation's adapter through a JSON request/response protocol (capabilities, decode, readTree, writeTree, exit), compares its canonical output with the cases in spec/ir/mck, skips cases for versions or node kinds the adapter does not claim, and writes a report that morphir mck report check gates. The kit is mostly v4; it has only a handful of @version:3 cases. This repository does not acquire the morphir CLI anywhere today.

Goals and non-goals

Goals: a v3 reader that needs nothing from the classic family; held to the shared MCK contract rather than to a local fixture set; v3 reading cases that every Morphir binding shares; a removal that leaves no ZIO in any published module.

Non-goals: a Kyo evaluator for Morphir IR; reading v3 format versions 1 and 2; v4 conformance of CodeModelCodecs (a follow-up: claiming v4 in the adapter); Scala Native for the reader (the code model has no Native build); migrating consumers' code; changing the v3 write projection beyond what canonical output needs.

Decisions

V3-1. Put the reader in model.compat.v3, built for JVM and Scala.js

model.compat.v3 already owns the v3 wire format in the write direction, and decision 0017 treats deprecated IR formats as wire projections at the edge of the code model. Reading the same format belongs in the same module, so v3 knowledge lives in one place. The module gains a Scala.js variant because the classic JSON codecs it replaces also published for Scala.js.

Alternatives: port model.lowering onto Kyo and keep its name (the name describes lowering classic objects, which will no longer exist); a new model.ingest.v3 module (splits one format across two modules).

V3-2. Decode straight into the code model, with no intermediate v3 model

The reader parses with Kyo JSON into a generic JSON tree and walks v3's tagged-array encoding (["Library", …], ["Reference", …]) directly into code-model values, applying V3Lowering's rules as it goes: attributes erased, a typed value's type kept as its inferred type, constructors and bundle packages sorted by name, the package version left at the existing placeholder. The node tags and field layouts come from the classic v3 decoder while it exists; the MCK cases are the contract afterwards.

Alternatives: port the classic v3 IR types to Kyo and keep two-step decoding (a second IR model to maintain, which is what this change removes); schema-derived codecs (v3 is a positional, tag-in-array encoding that derivation does not produce).

V3-3. Typed errors with a location and the kit's codes; format version 3 only

Decoding returns a Result with a small error type: malformed JSON, unknown tag, wrong shape, and unsupported format version, each carrying a JSON path to the fault. The MCK protocol carries a diagnostic code as a free string, and each kit case names the code it expects (rejects with <code>). Today's kit names only YAML codes; the upstream v3 cases (MCK-2) define the v3 ones, and the reader's errors carry those codes so the adapter answers a rejection case without translation. No exception escapes. Only formatVersion 3 is accepted, because current morphir-elm writes it.

Accepting versions 1 and 2 would mean porting two more decoders for input no known consumer produces; a consumer holding v1 or v2 IR can regenerate it with current morphir-elm.

MCK-1. An unpublished JVM adapter module, started through its Mill launcher

A small JVM module (morphir.model.compat.v3.mck, not published) speaks the IR adapter transport that finos/morphir defines in spec/mck/cli-contract.md: newline-delimited JSON requests on standard input, one response line each on standard output. capabilities claims version 3, the json profile, the single layout and the node kinds the reader supports. decode decodes with the v3 reader and answers with canonical v3 JSON written through V3WireProjection. readTree and writeTree are not claimed. The runner starts it through the script Mill's launcher task produces, so no assembly or Native image is needed. Unit tests for the protocol handling run in test-jvm like any other module.

Alternatives: an adapter inside the published module (puts a CLI entry point into a library); a Scala.js adapter on Node (adds a runtime to the job for no extra coverage of shared code).

MCK-2. Add the v3 reading cases to the kit upstream

The @version:3 cases that hold a reader to real morphir-elm output belong in finos/morphir's spec/ir/mck, where every binding's v3 reader is measured against them, not in a fixture set private to this repository. A finos/morphir PR adds them: per-node @semantic and @spelling cases in the topic files, and whole-library documents under documents/ generated by morphir-elm from the projects in examples/morphir-elm-projects (generated once, before Phase 2 deletes those projects). Case IDs and prose follow the kit's authoring rules, and morphir mck check spec/ir/mck must pass upstream.

Alternative: keep the cases local (shared bindings would not benefit, and morphir-scala would maintain a second runner and report format).

MCK-3. Acquire a pinned Morphir CLI and run MCK in its own CI job

The morphir CLI is downloaded at a pinned version and verified against a pinned SHA-256 through the repository's existing toolchain acquisition, cached like the other verified tools. A new mck-ir job builds the adapter launcher, runs morphir mck run --suite ir --strict with the CLI's embedded kit, writes the JSON and HTML reports as job artifacts, and gates on morphir mck report check. The ci aggregate gate requires it. The reader's unit tests stay in test-jvm, which needs no Node and no Morphir CLI. A mck:run mise task runs the same steps locally.

Phase 1 pins the current CLI, whose kit has few v3 cases. Phase 2 cannot start until the pin moves to a release that ships the MCK-2 cases and the job passes them.

Alternatives: running MCK inside test-jvm (adds a CLI download and a second process to the main JVM gate); a vendored kit snapshot via --kit (two things to keep in step instead of one pin).

DEP-1. Deprecate through documentation and metadata, not @deprecated

The deprecation milestone changes the CHANGELOG, each classic module's README text and entry-point scaladoc, and the POM description (prefixed with "Deprecated:", which Maven Central shows on the artifact page). It does not annotate classes with @deprecated: the build runs with -Werror, so annotating ~490 files would break every internal use and its tests for no benefit to consumers who read the notice anyway.

Alternative: @deprecated on entry points with a -Wconf exemption inside the classic modules (more change for the same consumer-facing signal).

REM-1. Phase 2 removes by dependency, including the example projects

Removal deletes the classic module directories, the classic-only build wiring (MorphirRootMvnDeps, MorphirTestsTestMvnDeps*, the classic fixture and discovery traits and RuntimeTestDiscovery), the runtime-generated-fixtures, runtime-tests and morphir-elm-projects jobs and their entries in the ci aggregate gate, the test:runtime-jvm, build:elm and build:morphir-elm tasks and their lines in ci:local, examples/morphir-elm-projects, and the ZIO suites and version pins once a full resolve shows nothing else uses them. morphir-elm/sdks goes too unless the Mill plugin tests that name morphir-unit-test need the repository module. The publish set shrinks on its own, because it selects modules by path prefix. The unwired classic leftovers (morphir/meta, morphir/elm/facade, morphir/toolkit) go too, which absorbs intent 0028.

REM-2. Cut knowledge.logic loose in Phase 1

Its dependency on the root module is unused, so it goes in Phase 1 rather than waiting. This removes ZIO from a Kyo-side library one milestone early and keeps the removal PR to deletions only.

DOC-1. Record the retirement in the knowledge base, and update the guidance that assumes ZIO

Phase 1 adds a kind: deprecation intent and a kind: removal intent; the removal intent supersedes 0028. Phase 2 updates AGENTS.md (the testing section's "ZIO Test elsewhere", "Prefer ZIO or Kyo libraries", the CI job list), module CONTRIBUTING files, and the Capability and Design Note pages that describe the classic library, and releases both intents with links to the Capability that describes v3 reading.

Risks and trade-offs

RiskMitigation
Phase 2 waits on an upstream PR and a Morphir CLI release that this repository does not control. Phase 1 ships and deprecates without it. The upstream PR is opened during Phase 1, so it has the deprecation milestone's lifetime to land.
The kit's v3 cases miss a node shape, so the reader diverges on input nobody tested. The upstream documents are whole morphir-elm libraries, including evaluator-tests, which was written to drive the classic evaluator through its expression forms. Per-tag unit tests ported from the classic decoder run in test-jvm. An unknown tag fails with a typed error naming it, not a wrong result.
Canonical v3 output differs from the kit's spelling byte for byte (key order, spacing). The adapter writes through V3WireProjection and a canonical printer; the kit allows one trailing newline and nothing else, so mismatches surface as named failing cases in the report.
Consumers of the classic evaluator lose it, and the Kyo side has no replacement. The deprecation milestone says so explicitly; those consumers can stay on the last classic release. A Kyo evaluator is separate work.
Rejecting v3 format versions 1 and 2 breaks someone holding old IR. The error names the version and the fix (regenerate with current morphir-elm).
Removing the ZIO pins breaks a module that resolves ZIO transitively for another reason. Phase 2 runs the classpath check from the published-library-families spec across every module before deleting the pins.

Migration plan

  1. Phase 1 (one or two PRs): the reader and its unit tests (V3-1 to V3-3), the adapter and the mck-ir job (MCK-1, MCK-3), REM-2, the deprecation notices (DEP-1) and the two intents. Released as the next milestone, 0.5.0-M12. In parallel, the upstream PR for MCK-2.
  2. Gate: the deprecation milestone is on Maven Central, and the pinned Morphir CLI ships the upstream v3 cases with the adapter passing them.
  3. Phase 2 (one PR): REM-1 and DOC-1. Released as a later milestone, labelled breaking.
  4. Rollback. Before release, revert the Phase 2 merge. After release, consumers pin the last milestone that published the classic artifacts; nothing on Maven Central is removed or changed.
